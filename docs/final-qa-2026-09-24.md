# IRIS Ops Studio 1.2.0 — final QA follow-up

Status: **unpublished candidate; publication still requires explicit approval**.
This report is specific to the corrected 1.2.0 source tree and a fresh,
disposable IRIS Community 2026.2 container. It does not replace the earlier
fixture-mutation evidence in `validation-report.md` and
`web-app-development-validation.md`.

## Defects found and corrected

1. The guided user-role dropdown still offered the built-in `IAM`, `SuperUser`,
   and installer `irisowner` identities, contrary to its own safety text. All
   observed built-in identities are now excluded, the workflow is disabled
   when no eligible user exists, and the action handler independently rejects
   a protected target. No built-in account was changed.
2. Incident Timeline treated normal names such as `EnsAlert` and a task named
   `Purge errors and log files` as warnings or critical signals. Matching now
   requires whole status words. On the fresh live container, the count fell
   from three signals to one actual failed-login event.
3. Audit and task free-text fields were HTML-escaped but not passed through
   credential-shaped-text redaction before Timeline display. Normalization
   now redacts those fields; generic table cells also redact recognizable
   credential text. This is a defense for known patterns, not a guarantee that
   arbitrary secrets can never appear in user-authored text.
4. A guided task `Run` readback stopped after about three seconds, while the
   IRIS Task Manager may need up to 60 seconds to pick up a scheduled run.
   The first live run completed successfully only after the app had recorded
   `pending`, so its journal entry did not become verified. Task-run readback
   now allows 75 one-second attempts; other mutations keep their short retry
   window. On the second live run, the journal recorded `executed / verified`
   only after a new successful `LastFinished`, which was independently read
   from `%SYS.Task`. A timeout still remains `pending`, not a false success.
5. A previous operation's success toast could remain visible while a new
   asynchronous request was still waiting. Submission now replaces it
   immediately with an amber "result not yet verified" progress notice, then
   shows the actual readback outcome. This was observed during the second
   live task run.

## Evidence

- Seven JavaScript syntax checks and **72/72** Node tests passed after the fixes.
  Imported-module line coverage was **99.00%**, branch coverage **80.39%**,
  and function coverage **98.28%**. Browser `app.js` is excluded from those
  percentages.
- A new image was built from the corrected tree and installed in a separate
  IRIS 2026.2 container with no mounted volumes and a loopback-only port. It
  became Docker-healthy without restarts. The installed `app.js` and
  `operations.js` SHA-256 values matched the corrected local files. Static
  pages returned HTTP 200; an unauthenticated SysAdmin API read returned 401.
- The operator authenticated directly in the browser without sharing a
  password. All ten areas loaded live IRIS data. System processes and web
  applications showed disabled guided actions. The Access workflow had no
  eligible built-in user after the correction. A read-only Explorer `GET /info`
  returned API version 2.
- Access Control, Incident Timeline, and Web apps were reviewed at exact
  1440×900 and 390×844 browser viewports. No page-level horizontal overflow
  was measured; wide tables scrolled inside their own containers. The browser
  console contained no captured warnings or errors.
- The fresh container log showed an IRIS warning that its primary and alternate
  journal directories coincide. This is a base-instance configuration warning,
  not an observed Ops Studio application error; it should be assessed before
  relying on that container for durable data.
- With explicit owner approval, three objects were created only in this fresh
  disposable container: disabled `IrisOps_TestUser` with no roles,
  `IrisOps_TestRole` with no resources or granted roles, and
  `IrisOps_TestResource` with no public permission. Their names were checked
  absent first. No built-in identity, system resource, or older container was
  changed.
- In the live guided Access workflow, assigning and revoking the test role on
  the test user both returned `executed / verified`. Granting `RWU` on the test
  resource, reducing it to `R`, and revoking it from the test role each returned
  `executed / verified`. After every operation, a separate published IRIS
  security API read confirmed the actual role/permission state. The Incident
  Timeline showed five verified session operations and corresponding IRIS audit
  records; the browser console had zero captured errors.
- A role-resource preview was deliberately made stale by changing only the
  disposable role's description through the published IRIS API. Submission
  returned `blocked / stale` in the session journal; independent IRIS readback
  confirmed the requested resource grant was absent. The guard code rejects
  this state before dispatching the PUT; no network packet capture was taken.
  The original description was then restored and independently verified.
- Final independent reads confirmed the test user remains disabled with no
  roles; the test role has its original description, no resource permissions,
  and no granted roles; and the test resource has no public permission. The
  three named fixtures remain in the disposable container for review, not
  deleted. Container health remained `healthy` with zero restarts and no
  mounted volumes.
- On the same corrected 52785 container, a separate no-op task fixture
  (`IrisOps v1.2 QA Task 52785`, ID 1000, namespace USER) was created with a
  future start date. Its class was compiled only into this disposable instance,
  not added to the release package. Guided Suspend and Resume both reported
  verified readbacks; independent `%SYS.Task` reads confirmed `Suspended=1`
  then `0`. Guided Run initially remained *verification pending*, correctly
  refusing to equate scheduling with completion. After the IRIS Task Manager
  executed it, `LastFinished` advanced from `0`, `Status=1`, and the task
  result was `Success`; the UI then displayed the new finish time. The
  [official Task Manager guide](https://docs.intersystems.com/irislatest/csp/docbook/DocBook.UI.Page.cls?KEY=GSA_manage_taskmgr)
  documents polling intervals of up to 60 seconds. The disposable task was
  suspended again after the test, and `Suspended=1` was independently read
  back to prevent further automatic runs.
- A separate finite-lived USER process fixture (PID 1418,
  `IrisOps.ValidationFixture.1`) was checked by PID, namespace, and routine
  before use. The guided Suspend operation changed its observed state from
  `HANG` to `SUSP`; guided Resume changed it back to `HANG`. Both reported
  verified readbacks. The process was **not** terminated as part of this test;
  it exited naturally after its finite loop, confirmed absent by OS PID check.
  The browser console still had zero captured warnings or errors after these
  checks.
- The final task-poll and progress-notice correction was hot-applied only to
  three static assets (`app.js`, `operations.js`, `styles.css`) in this same
  disposable container. Copies of their prior versions were saved first; the
  installed file hashes match the corrected local source. The container stayed
  healthy with zero restarts and no mounts. A separate image was then rebuilt
  from the final source and started as a second disposable container on
  loopback port 52786. It became healthy without restarts or mounts, served the
  portal with HTTP 200, returned HTTP 401 for an unauthenticated SysAdmin API
  read, and its three installed asset hashes matched the final source. That
  second container was stopped after the packaging check, not deleted; the
  live-tested 52785 container remains running.
- With specific owner approval, the dedicated `/csp/irisops-testweb` fixture
  (namespace USER, password authentication, no dispatch class) was enabled
  and then disabled through the guided UI. Both operations returned
  `executed / verified`. Separate `Security.Applications.Get` reads confirmed
  `Enabled=1` and then `Enabled=0`; namespace, authentication, description,
  and empty dispatch class were unchanged. The final UI row was Disabled.
- Final independent security reads still found `IrisOps_TestUser` disabled
  with no roles, `IrisOps_TestRole` with no resources or granted roles, and
  `IrisOps_TestResource` with no public permission. The disposable task was
  suspended, the process had exited naturally, and the web app was disabled.
  Browser console: zero captured errors or warnings. The container remained
  healthy, with zero restarts, zero mounts, and only a loopback port. In its
  recent Docker log there were zero error lines and one IRIS warning about
  coincident primary/alternate journal directories.

## Limits and remaining gate

- Live user-role and role-resource mutations, including one stale-preview
  rejection, plus process Suspend/Resume and task Suspend/Resume/Run, are now
  verified on the 52785 disposable container. Web-app enable/disable was also
  verified there, and the fixture returned to Disabled. The final task-poll
  correction was validated live as a hot update, and the same final assets
  were freshly built and started in the independent 52786 container. The
  latter packaging check did not repeat authenticated mutations. No real
  identities, system processes, or system tasks were used for the fixture
  tests.
- REST Management API discovery remained independently unavailable to the
  authenticated session. The SysAdmin registry still loaded; REST discovery
  is optional and must not be described as universally available.
- The application does not implement server-enforced per-tab read-only mode,
  atomic compare-and-set for process IDs, or per-run task correlation. In-place
  upgrade from a public older version was not reproduced. The 75-second task
  readback window can still return `pending` for a genuinely longer task; it
  does not silently claim verification.
- No test can establish that all defects or all possible secret leaks are
  absent. Keep publication subject to final owner review and approval.
