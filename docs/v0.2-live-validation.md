# IRIS Ops Studio v0.2 — live validation checklist

Run this checklist only against a disposable InterSystems IRIS 2026.2 instance.
Do not use production users, roles, resources, processes, scheduled tasks, or
credentials.

## Fixtures

Create dedicated, non-system fixtures before opening Ops Studio:

- user: `IrisOps_TestUser`;
- roles: `IrisOps_TestRole` and `IrisOps_TestRole2`;
- resource: `IrisOps_TestResource` with no public permission;
- a harmless scheduled task owned by the test environment;
- a disposable process whose only purpose is suspend/resume/terminate testing.

Never target `_SYSTEM`, `Admin`, `CSPSystem`, a role beginning with `%`, a
system maintenance task, or a normal application process.

## Automated baseline

From the repository root:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\validate-windows.ps1
```

Pass criteria:

- all 49 automated tests pass;
- `index.html`, `styles.css`, `api.js`, `sanitization.js`, `operations.js`, and
  `app.js` return HTTP 200 from `/csp/ops/`;
- the report contains no password, bearer token, refresh token, or private key.

## User-role workflow

1. Connect Ops Studio to the disposable instance and open **Access control**.
2. Select `IrisOps_TestUser` and `IrisOps_TestRole`.
3. Choose **Assign role**.
4. Confirm that the preview shows the current Roles array and the expected array.
5. Confirm that the request body contains only documented mutable user fields.
6. Enter the exact target-bound phrase and execute.
7. Require a `verified` journal result from `GET /v2/security/user`.
8. Repeat with **Revoke role** and require a second `verified` result.
9. Independently confirm that unrelated user fields did not change.
10. Open the confirmation dialog again, change the test user independently,
    then submit the old preview. Require `blocked / stale` and confirm that no
    `PUT` was sent.

## Role-resource workflow

1. Select `IrisOps_TestRole`, `IrisOps_TestResource`, and `RWU`.
2. Choose **Grant / update** and inspect the before/expected comparison.
3. Execute and require a `verified` readback from
   `GET /v2/security/role`.
4. Change the permission to `R`; require another verified readback.
5. Revoke the resource; require a verified absence result.
6. Confirm independently that any unrelated resource grant remains unchanged.
7. Repeat the stale-preview test above against the disposable role.

## Process and task readback

1. Confirm that a process reporting `CanBeSuspended=false` or
   `CanBeTerminated=false` exposes the corresponding disabled action.
2. Suspend the disposable process and require state `SUSP` in the readback.
3. Resume it and require a non-suspended state.
4. Terminate it and require HTTP 404 from `GET /v2/process` as positive proof.
5. Suspend and resume the disposable task; verify its `Suspended` boolean.
6. Run the task. A changed `LastStarted` with status `-1` must remain `pending`;
   require a new `LastFinished`, non-failure status, and successful `Error`
   value before recording completion as verified.

## Incident Timeline

1. Open **Logs & audit** after the operations above.
2. Confirm that Audit, Tasks, and Ops Studio each report source health
   independently.
3. Filter by each source, each severity, the fixture name, and a correlation ID.
4. Temporarily test with an account that lacks one source privilege. The failed
   source must show unavailable without suppressing the other sources.
5. Confirm that every operation entry identifies demo/live mode, instance, and
   actor, and contains no request secrets or credentials.

## Visual QA

Check at both 1440×900 and 390×844:

- Access control tables and both mutation cards;
- Incident Timeline controls and horizontal table access;
- the four-stage preflight dialog;
- the top-bar Journal counter;
- connection and confirmation dialogs at maximum content height.

No page-level horizontal overflow is acceptable. Table-local horizontal
scrolling is acceptable on narrow viewports.

## Cleanup and release decision

After validation, either remove the disposable fixture/container/volume under
an explicitly approved cleanup plan or stop and retain the isolated container
and volume for recovery. Record which option was chosen and exclude retained
runtime data from release artifacts. Sanitize evidence before sharing.

Mark the validated release **READY FOR PUBLICATION APPROVAL** only when every
section above passes and retained runtime data is safely isolated. Any failed
readback, overwritten unrelated permission, leaked secret, or inaccessible
mobile control is a release blocker.
