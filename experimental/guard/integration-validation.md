## Implementation in requested order

1. The actual `web/index.html` and `web/assets/app.js` now have an opt-in
   experimental wallet profile, not a replacement mock screen or an iframe.
   It reuses Connection settings, the wallet form, typed confirmation, navigation
   and the session journal. Only IrisOps_GuardProbeWallet and the two existing
   disposable policy resources remain eligible on the server.
2. The server owns the read-only channel, temporary write permission, exact preview,
   precondition check, single dispatch and readback. The new WalletGuard adapter
   holds the private proof internally; preview objects passed to the main UI and
   its journal never include that key.
3. This profile never logs into /api/admin from the browser. The ordinary client
   is replaced with a frozen denying adapter. Generic operation preparation,
   direct readback and Explorer dispatch cannot fall back to the native API.
   Missing integration assets or an unavailable guard leave the flow blocked.
4. Real-IRIS tests exercise the actual existing dialogs, expiry, revocation,
   shared-browser tabs, interrupted requests and durable read-only recovery.
   See evidence status below; passing this flow does not qualify the whole product.

## Behavior and limits

- Connection creates a new read-only channel. Authorization is deliberately
  limited to 60 seconds and previews to 30 seconds; no hidden credential refresh.
- Explicit reconnect preserves tab-scoped recovery keys but invalidates approvals.
  Explicit disconnect forgets keys, clears visible receipt details and local
  journal summaries. Historical server receipts are not deleted.
- The native CSP cookie can be shared by browser tabs. Reconnecting one tab may
  invalidate another tab's channel/preview; this is fail-closed, not fully isolated
  per-tab session UX. A new tab never inherits a write-enabled UI state.
- Recovery preserves original UNKNOWN state when a later observation matches.
  If IRIS finished and verified a change but its response was lost, recovery can
  show that already-saved VERIFIED receipt. It does not resend or infer causation.
- Non-wallet pages are deliberately unavailable in this isolated profile. The
  normal published application remains unchanged and is NOT covered by this guard.
- Native /api/admin retains its own independent permissions. An authorized
  operator using another client is not made globally read-only by this UI.
- The possession-proof and browser-trust limits in
  [recovery-validation.md](recovery-validation.md) still apply.
- Installation/upgrade, HTTPS, credential renewal, native audit linkage, broader
  targets/operations, proof lifecycle and crash/disk/clone scenarios remain gates.

## Defect found and fixed

The first integrated run failed before any mutation because the transport returns
`name` while the existing wallet validator expects `Name`. The adapter now
validates the exact guard response fields and target, then explicitly converts
that metadata contract. A regression test checks the actual shape and rejects
wrong targets and extra fields. Failed initial run is not release evidence.
